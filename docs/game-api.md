# Проект игрового контракта

Статус: архитектурная основа для командной разработки. Типы ниже ещё не реализованы;
точные сигнатуры и игровые значения фиксируются задачей API после согласования требований.

## Границы данных

| Тип | Назначение | Владелец изменений |
|---|---|---|
| `Bounds2` | Валидный прямоугольник в X/Y с положительными размерами; правила касания/пересечения | Core |
| `LevelDefinition` | Неизменяемая геометрия уровня, spawn и согласованные игровые области | Core |
| `PlayerState` | Положение, скорость, размеры коллайдера, состояние опоры | Core |
| `GameInput` | Горизонтальное намерение и одноразовые команды; без enum клавиатуры | Core |
| `GameSession` | Состояние текущего сеанса и переходы между согласованными состояниями | Core |
| `SimulationSettings` | Проверяемые параметры движения и допустимый шаг | Core |
| `GameSimulation` | Обновление игрового состояния по команде и фиксированному шагу | Core |
| `InputMapper` | Перевод `InputSnapshot` движка в игровые намерения | App |
| `FixedStepRunner` | Накопление времени, ограничение догоняющих шагов, доставка одноразовых команд | App |
| `GameScenePresenter` | Синхронизация сцены и камеры с состоянием игры | App |

Core не зависит от движка, OpenTK, окна, файловой системы или реальных часов.
Состояние симуляции не хранит SceneObject, MaterialData, callbacks окна или GPU-ресурсы.
Представление не изменяет физическое состояние в обход симуляции.

`GameInput` не оборачивает `InputSnapshot`: это отдельное значение Core, содержащее
нормализованное намерение движения и только согласованные одноразовые игровые команды.
Например, кандидаты после принятия управления — MoveAxis в [-1,1], JumpPressed и RestartPressed.
Конкретные имена/сигнатуры закрепляет T02. Николай реализует преобразование в App;
Владимир потребляет готовый GameInput в симуляции без чтения Engine.Input.

## Предлагаемые сигнатуры для согласования

Это псевдокод контракта, не добавление реализованных C#-типов. Конкретные команды
в GameInput зависят от T01; численные пределы определяются T02, но единицы измерения едины.

```csharp
// Platformer.Core: положения/размеры в мировых единицах, скорость в единицах/секунду.
public readonly record struct Bounds2(Vector2 Center, Vector2 Size);
public readonly record struct GameInput(float MoveAxis, bool JumpPressed, bool RestartPressed);
public sealed class SimulationSettings
{
    public float FixedStepSeconds { get; }
    // Другие параметры и допустимые диапазоны фиксируются после принятия T01.
}
public sealed class GameSimulation
{
    public GameSimulation(LevelDefinition level, SimulationSettings settings);
    public PlayerState Player { get; }
    public GameSession Session { get; }
    public void Step(GameInput input); // использует settings.FixedStepSeconds
}
```

App получает величину шага из того же SimulationSettings, не хранит вторую независимую
константу. На границе Engine deltaSeconds измеряется в секундах; FixedStepRunner переводит
кадровое время в целое число вызовов Step. Тесты используют те же настройки и искусственное время.
Это устраняет расхождение частоты между Core и App; значение по умолчанию не назначается до T02.

## Требуемые инварианты контракта

- X/Y — игровая плоскость, Y вверх; физика не зависит от визуальной толщины по Z.
- Данные уровня проходят валидацию до начала сеанса; изменяемые входные коллекции не меняют уровень задним числом.
- При одинаковом начальном состоянии и последовательности команд/шагов результат воспроизводим
  в пределах документированных допусков; межплатформенная битовая идентичность не обещается.
- Симуляция использует конечный положительный FixedStepSeconds из настроек в пределах контракта. Неверный ввод
  отклоняется до частичной мутации состояния; типы исключений фиксируются в API-задаче.
- Коллизии определяют касание границ, начальное пересечение, порядок обработки платформ и опору;
  изменение порядка платформ не должно давать случайный другой результат.
- Одна команда нажатия потребляется не более одного раза независимо от количества sim ticks за кадр.
- При потере фокуса App очищает очередь команд и накопленное время; поведение самого сеанса
  при паузе/возврате фиксируется требованиями, а не угадывается исполнителями.
  Возврат фокуса не воспроизводит прежние команды; зажатые при активации клавиши
  принимаются движком только после отпускания и нового нажатия.
- Перезапуск, если включён в согласованные требования, восстанавливает всё состояние сеанса,
  а не только позицию; прежняя команда прыжка не переносится в новый сеанс.

## Что нужно решить до реализации

Привязки клавиш, модель прыжка, численные параметры, схема уровня, камера при движении,
победа/поражение/перезапуск и обратная связь игроку проходят задачу требований.
Затем задача API фиксирует реальные сигнатуры, ошибки, допуски и проверяемые примеры.
Движковый ввод уже доступен; менять его API ради игровых правил не требуется.
