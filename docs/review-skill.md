# Прожарка PR (`roast-my-pr`)

Самопроверка изменений перед PR тремя независимыми ревьюерами. Вызывается только пользователем:
`/roast-my-pr [точка отсчёта] [тикет]` (скилл `.agents/skills/roast-my-pr`) или просьбой агенту
«выполни docs/review-skill.md». Оба аргумента необязательны.

Ты — **автор** изменений. Ревью делают три **головы**: Standards, Spec и Bugs — ревьюеры
с чистым контекстом, которые не видели, как писался код. Они только читают и докладывают;
исправляешь ты.

Головы Standards и Spec адаптированы из `code-review` Matt Pocock (MIT). Голова Bugs в Claude Code —
встроенный `/code-review high`; в остальных агентах — раздел «Голова Bugs», адаптированный из плагина
`code-review` Anthropic (Apache 2.0, изменён под локальный diff); см. [THIRD_PARTY.md](../THIRD_PARTY.md).

## Шаги автора

### 1. Зафиксируй diff

- Точка отсчёта: из аргумента, иначе `git fetch --prune` и `BASE=$(git merge-base origin/main HEAD)`.
- Проверь `git rev-parse <base>`. Diff для ревью — `git diff <base>`: коммиты ветки плюс
  незакоммиченные правки. Новые файлы вне индекса — `git ls-files --others --exclude-standard`.
- Пустой diff или неразрешимая ссылка — остановись и скажи пользователю.

### 2. Найди тикет

По порядку: аргумент → номер в имени ветки (`feature/9-...`) → `#N` / `Closes #N` в коммитах.
Получи текст: `gh issue view N --comments`; дополни строкой задачи из
[project_plan.md](../project_plan.md) и [task-guide.md](task-guide.md).
Не нашёл — спроси пользователя; если тикета нет, голова Spec не запускается, отметь это в отчёте.

### 3. Собери стандарты

Файлы, где записано, как писать код: всегда [AGENTS.md](../AGENTS.md) и
[CONTRIBUTING.md](../CONTRIBUTING.md), плюс документы, которые они называют обязательными
или которые затрагивает diff ([architecture.md](architecture.md),
[engine-integration.md](engine-integration.md), контракты `docs/*-contract-*.md`, `.editorconfig`).

### 4. Выпусти три головы параллельно

Каждая голова — отдельный сабагент со свежим контекстом и максимальным доступным reasoning
effort (в Claude Code — `high`), в режиме только чтения. Запусти все три одним сообщением
и дождись отчётов. Промпт головы:

```text
Ты ревьюер, а не автор. Только читаешь: не меняй файлы, не делай commit/push, не публикуй комментарии.
Прочитай docs/review-skill.md, раздел «Голова <Standards|Spec|Bugs>», и выполни его.
Diff: git diff <base>; новые файлы: <список или «нет»>; коммиты: git log <base>..HEAD --oneline.
Standards: список файлов стандартов.
Spec: номер тикета и его полный текст с комментариями.
Bugs: цель изменений одним абзацем из тикета.
```

**Bugs в Claude Code:** вместо сабагента по промпту выше в том же сообщении вызови встроенный
скилл `/code-review high` (через Skill tool, без `--fix` и `--comment`): он сам запускает
ревьюеров с чистым контекстом по текущему diff. Скилл недоступен — запусти Bugs по промпту выше.

Агент без сабагентов: выдай пользователю три готовых промпта и попроси прогнать каждый
в отдельном новом чате, затем вставить ответы сюда. Роль головы сам не исполняй.

Шаг завершён, когда есть три отчёта (или два и пометка «нет тикета»). Ошибка, пустой или
обрезанный ответ — не ревью: перезапусти голову.

### 5. Разбери каждую находку

Находка — гипотеза, а не приказ. Для **каждой** открой код и реши:

- **исправить** — дефект подтверждён;
- **отклонить** — опровергнут кодом, документом или тестом; запиши чем;
- **к пользователю** — продуктовая развилка, изменение scope тикета, правка `external/engine`
  или документированного контракта.

Шаг завершён, когда у каждой находки есть решение.

### 6. Исправь

Исправь всё из «исправить». Новый дефект сначала подтверди воспроизводящим тестом.
Затем прогони проверки из AGENTS.md («Работа и проверки») в объёме изменений.
Повторное ревью не запускай. Commit и push — только по правилам AGENTS.md.

### 7. Отчёт в чате

Отдельный раздел на каждую голову (`Standards`, `Spec`, `Bugs`), без смешивания и переранжирования:
таблица «находка (`файл:строка`) → решение → что сделано или почему отклонено».
В конце — итог проверок (при ошибках с фактическим выводом) и вопросы к пользователю.

## Голова Standards

Вопрос: соответствует ли diff документированным стандартам репозитория?

1. Прочитай каждый переданный файл стандартов целиком.
2. Пройди diff по файлам и hunk-ам; читай окружение, если без него правило не проверить.
3. Сверь каждый hunk с каждым правилом и со smell baseline ниже.

Пропускай то, что ловят tooling и CI (форматирование, сборка, `scripts/check_docs.py`),
и проблемы, существовавшие до diff.

**Smell baseline** (Фаулер, _Refactoring_, гл. 3). Документированный стандарт главнее: если он
разрешает то, что помечает baseline, smell не указывай. Smell — всегда judgement call
(«возможно, Feature Envy»).

- **Mysterious Name**: имя не раскрывает, что делает или хранит. → переименовать.
- **Duplicated Code**: одна форма логики в нескольких hunk-ах или файлах. → вынести общее.
- **Feature Envy**: метод больше работает с данными чужого объекта. → перенести к данным.
- **Data Clumps**: одни и те же поля/параметры ходят вместе. → собрать в тип.
- **Primitive Obsession**: примитив вместо доменного понятия. → маленький тип.
- **Repeated Switches**: один и тот же `switch`/`if`-каскад в нескольких местах. → полиморфизм или общая таблица.
- **Shotgun Surgery**: одно логическое изменение размазано по многим файлам. → собрать в модуль.
- **Divergent Change**: один файл меняется по нескольким несвязанным причинам. → разделить.
- **Speculative Generality**: абстракции и хуки под нужды, которых нет в тикете. → удалить.
- **Message Chains**: длинные `a.B().C().D()`. → спрятать за метод первого объекта.
- **Middle Man**: класс/функция только делегирует дальше. → вызывать цель напрямую.
- **Refused Bequest**: наследник игнорирует большую часть унаследованного. → композиция.

Отчёт до 400 слов. Каждая находка: `файл:строка` и цитата hunk-а; **hard** (нарушен
документированный стандарт — файл и правило) или **judgement** (smell, спорная трактовка);
исправление одной строкой. Нет находок — так и напиши, перечислив проверенные стандарты.

## Голова Spec

Вопрос: делает ли diff то, что просил тикет, — не меньше, не больше и правильно?

1. Выпиши из тикета каждое требование и критерий приёмки отдельной строкой, включая уточнения
   из комментариев. Если тикет ссылается на `docs/`, прочитай эти места.
2. Для каждого требования найди в diff реализацию и подтверждающий тест.
3. Для каждого изменения в diff найди требование, которое его оправдывает.

Отчёт до 400 слов, три раздела:

- **(a) Не сделано или частично** — требования нет в diff; код без теста или тест без кода — тоже сюда.
- **(b) Сверх тикета** — поведение, о котором тикет не просил (scope creep).
- **(c) Сделано неверно** — реализовано, но поведение расходится с текстом.

Каждая находка: цитата строки тикета, `файл:строка` (для (a) — где ожидалась реализация),
суть расхождения. Нет находок — так и напиши, перечислив сверенные требования.

## Голова Bugs

В Claude Code эту голову заменяет `/code-review high` (шаг 4); раздел — для остальных агентов.

Вопрос: есть ли в добавленном или изменённом коде реальные дефекты?

Работай в два прохода.

**Поиск.** Сначала только по diff: явные ошибки, которые видны без внешнего контекста.
Затем с контекстом: читай вызывающий и вызываемый код, чтобы найти неверную логику,
нарушенные инварианты, гонки, утечки ресурсов, ошибки границ и проблемы безопасности
в изменённом коде.

**Проверка.** Для каждой находки попытайся её опровергнуть: прочитай код вокруг, найди guard,
тест или контракт, которые делают её ложной. Оставь только находки, пережившие опровержение.

Указывай только **high signal**:

- код не скомпилируется или не разберётся (типы, неразрешённые ссылки, синтаксис);
- код даёт неверный результат или падает при конкретном, достижимом сценарии;
- однозначное нарушение правила из AGENTS.md, которое можно процитировать.

Не указывай:

- проблемы, существовавшие до diff;
- то, что выглядит багом, но корректно;
- придирки, которые senior-инженер не стал бы писать;
- то, что ловят компилятор, анализаторы или CI;
- общие замечания о качестве и покрытии тестами, если их не требует AGENTS.md;
- нарушения, явно подавленные в коде (например, suppress-комментарием).

Не уверен, что проблема реальна, — не пиши её: ложные находки тратят время автора.

Каждая находка: `файл:строка`, суть одним предложением, **сценарий отказа**
(входные данные или состояние → неверный результат или падение), чем подтверждено при проверке.
Нет находок — так и напиши.
