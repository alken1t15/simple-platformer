# План разработки 2D-платформера

Цель этого плана — распределить командную работу, определить архитектурные стыки,
зависимости и приёмку. Разработка игровой механики в рамках подготовки не выполняется.

## Подтверждённая основа

- C#/.NET 10; 2D-плоскость X/Y, фиксированная Z, боковая камера, существующий 3D-рендер.
- Отдельные Core, App и Tests; внешний движок подключён через закреплённый submodule.
- Публичный ввод принят в [PR движка №50](https://github.com/alken1t15/simple-3d-engine/pull/50).
- Интеграция ввода, боковая камера и Escape подготовлены в [PR игры №1](https://github.com/alken1t15/simple-platformer/pull/1).
- Состав и роли — [команда](docs/team.md); контракт — [проект API](docs/game-api.md);
  принятые факты и открытые решения — [требования](docs/requirements.md).

## Этапы без вымышленных дат

| Этап | Контрольный результат | Порядок |
|---|---|---|
| M1 — Требования и контракты | Согласованы правила игры, данные и API модулей | Сначала требования, затем API; QA готовит матрицу приёмки параллельно |
| M2 — Игровая реализация | Уровень, симуляция, input/fixed-step, представление и правила сеанса интегрированы | Модель уровня и App-цикл параллельны после API; физика зависит от геометрии; правила — от симуляции |
| M3 — Проверка и сдача | Регрессии, графический smoke, ручные протоколы, воспроизводимый запуск и материалы | CPU-проверки развиваются вместе с модулями; финальная приёмка после интеграции |

Сроки, длина спринта, оценки трудоёмкости и текущая доступность участников не заданы.
Этапы являются относительным порядком, не календарным расписанием. Исторический календарь
движка к игре не применяется. Числа FPS/coverage и аппаратные цели без требования не назначаются.

## Пакет задач

Переход M1 → M2 допускается после закрытия задач требований и API по следующим результатам:

- У каждой строки решений в requirements.md есть принятый ответ или явное исключение из MVP;
  перечислены проверяемые сценарии и целевые стенды.
- У типов API определены реальные сигнатуры, единицы измерения, валидация, исключения,
  допустимые диапазоны, допуски, шаг и правила касания/опоры.
- Зафиксированы обработка фокуса и одноразовых команд, порядок переходов и сброс состояния.
- Стыки согласованы владельцами Core/App через принятые PR; для чужого PR соблюдены два
  человеческих Approve, для собственных PR Team Lead действует описанное исключение.

Готовность отдельных зависимостей позволяет начать соответствующую задачу; календарные даты
не являются условием закрытия M1 и не придумываются ради перехода к реализации.

## Готовность проекта

Готовность означает выполнение согласованных критериев T01, принятые реализации,
успешные обязательные CI и фактическую ручную приёмку. Пустой шаблон, зелёный CPU-тест
или техническая сцена не доказывают готовность игры. Сдача не закрывается при открытых блокирующих дефектах.
